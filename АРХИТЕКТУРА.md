# Архитектура ДубинаОС

## 1. Слои

```
┌──────────────────────────────────────────────┐
│ Прикладные программы (на «Дубине»)           │
├──────────────────────────────────────────────┤
│ Стандартная библиотека «Дубины» (capability) │
├──────────────────────────────────────────────┤
│ Пользовательские службы:                     │
│  - служба разрешений                         │
│  - служба запуска                            │
│  - служба памяти                             │
│  - служба драйверов                          │
│  - служба файлов (ДубФС, FAT32)              │
│  - служба времени                            │
│  - служба окон (композитор)                  │
│  - служба логирования                        │
├──────────────────────────────────────────────┤
│ Микроядро (Rust no_std)                      │
│  - планировщик                               │
│  - управление памятью (paging, физ.память)   │
│  - IPC (синхронные/асинхронные сообщения)    │
│  - capability-таблица                        │
│  - обработка прерываний                      │
├──────────────────────────────────────────────┤
│ Загрузчик (свой):                            │
│  - x86 Legacy BIOS (MBR + Stage2)            │
│  - x86 UEFI                                  │
│  - aarch64 (UEFI + raw)                      │
└──────────────────────────────────────────────┘
```

## 2. Микроядро

### 2.1. Системные вызовы (минимальные)
```
ipc_отправить(порт, сообщение)             # синхронная отправка
ipc_получить(порт)                         # синхронный приём
ipc_вызвать(capability, метод, аргументы)  # высокоуровневый вызов через capability
уступить()                                 # передать процессор другому потоку
завершить(код)                             # завершить поток
```

Всего ~20 системных вызовов. Всё остальное — через сообщения службам.

### 2.2. Capability-таблица
У каждого процесса своя таблица capability (как у файловых дескрипторов в POSIX, но типизированных и непросматриваемых процессом напрямую).

| Capability | Описание |
|---|---|
| `Порт` | Канал IPC к другому процессу/службе |
| `Память` | Регион физической или виртуальной памяти |
| `Поток` | Управляющий хэндл потока |
| `Прерывание` | Линия прерывания (для драйверов) |
| `MMIO` | Регион memory-mapped I/O |

Capability **неподделываемы**: значение — это индекс в защищённой таблице ядра, а не указатель.

### 2.3. Память
- **Физическая**: bitmap free-page allocator. 4К страницы.
- **Виртуальная**: 4-уровневые таблицы (x86_64), 4-уровневые VA48 (aarch64).
- **Адресное пространство** на каждый процесс. Ядро отображено в верхнюю половину (неизменно).
- **Стек** программы: фиксированный, защищён неотображённой страницей-стражем (guard page).
- **Куча**: раздаётся службой памяти; для пользовательских программ это просто capability `Память`.

### 2.4. Планировщик
- Многоуровневая очередь обратной связи (как в Win11): чем больше поток ждал I/O, тем выше его динамический приоритет.
- Кванты времени динамически подстраиваются под нагрузку (как «timer coalescing» в Win11) — для энергоэффективности.
- Для real-time — отдельный класс с фиксированным приоритетом и SCHED_FIFO семантикой.

### 2.5. IPC
- **Синхронные сообщения**: `ipc_send_recv` — атомарно отправить и получить ответ. Самый быстрый путь.
- **Асинхронные**: очередь сообщений на порту, потоки могут спать в ожидании.
- **Передача capability** — через сообщение с особым типом. Получатель получает новый индекс в своей таблице.

## 3. Службы

### 3.1. Служба разрешений (`служба.разрешения`)
- Хранит манифесты установленных программ.
- При запуске программы проверяет: какие capability запрашивает манифест, и выдаёт ли система их этому пользователю/программе.
- Может временно расширять/сужать capability (sandbox-режимы).

### 3.2. Служба запуска (`служба.запуск`)
- Загружает файл `.дубп` (исполняемый формат «Дубины»).
- Проверяет подпись.
- Создаёт адресное пространство, отображает код и данные.
- Получает у службы разрешений capability по манифесту.
- Стартует поток с переданными capability.

### 3.3. Служба памяти (`служба.память`)
- Получает запросы на выделение страниц.
- Реализует кучу для программ.
- Отслеживает использование.

### 3.4. Служба драйверов (`служба.драйверы`)
- Перебор PCI/PCIe и DT (на ARM).
- Сопоставление устройств и драйверов по VID/PID.
- Загрузка драйверов (как обычных программ с особыми capability `MMIO` и `Прерывание`).

### 3.5. Служба файлов (`служба.файлы`)
- Маунтит ДубФС, FAT32, virtio-fs.
- Предоставляет capability `Файл` через капиб-вызов `открыть(путь, режим)`.

### 3.6. Служба окон (`служба.окна`)
- Композитор. Программы рисуют в свои буферы; служба окон собирает финальный экран.
- Окна — это capability, выданный службой окон. Без него — нет рисования.

## 4. Файловая система ДубФС

- **Журналирование** — full data journaling по умолчанию.
- **B+ деревья** для каталогов (быстрый поиск даже при миллионах файлов в каталоге).
- **Inodes** размером 256 байт, расширенные атрибуты внутри.
- **CoW** (copy-on-write) для снимков и дешёвых копий.
- **Шифрование AES-XTS** на уровне блоков (опционально, по разделу).
- **Контрольные суммы BLAKE3** на каждый блок (защита от bit-rot).
- **Сжатие**: Zstd по умолчанию для определённых типов файлов.
- **Размер блока**: 4 КБ.
- **Журнал**: круговой, размер = 1% размера ФС.

Ограничения:
- Макс. размер файла: 2^63 байт.
- Макс. размер ФС: 2^64 блоков * 4 КБ.
- Макс. длина имени: 255 символов UTF-8.

Для совместимости с UEFI ESP — отдельный драйвер FAT32 (только чтение).

## 5. Загрузчик

### 5.1. Legacy BIOS (x86)
1. **MBR** (512 байт, в секторе 0): загружается BIOS в `0x7C00`, переходит в защищённый режим, читает Stage2 с диска.
2. **Stage2**: переходит в long mode, парсит файловую систему загрузочного раздела (FAT32), читает ELF-файл ядра, отображает страницы, прыгает в `_начало_ядра`.

### 5.2. UEFI (x86_64 и aarch64)
1. UEFI приложение `BOOTX64.EFI` / `BOOTAA64.EFI`, написанное на Rust с использованием `uefi` crate.
2. Получает memory map, открывает корневую ФС, читает ядро.
3. Устанавливает GOP framebuffer.
4. Выходит из boot services, прыгает в ядро с передачей структуры `НачальныеДанные`.

### 5.3. ARM (aarch64)
- Свой загрузчик, совместимый с QEMU `virt` (стартует на `0x40080000` в EL2).
- Опускается в EL1, настраивает MMU, прыгает в ядро.

## 6. Передача данных загрузчик → ядро

Структура `НачальныеДанные` (в общей памяти, указатель в RDI/X0):
```rust
#[repr(C)]
pub struct НачальныеДанные {
    pub магия: u64,                   // 0x4475_6269_6E61_5F4F53 = "Дубина_OS"
    pub версия: u32,
    pub архитектура: u32,             // 1=x86_64, 2=aarch64
    pub карта_памяти: КартаПамяти,    // диапазоны физической памяти
    pub адрес_видео: u64,             // framebuffer (0 если нет)
    pub формат_видео: u32,
    pub ширина: u32, pub высота: u32, pub шаг: u32,
    pub адрес_acpi: u64,              // RSDP (0 если нет)
    pub адрес_dtb: u64,               // device tree blob для ARM (0 если нет)
    pub командная_строка: [u8; 256],
}
```

## 7. Безопасность

- **Stack canaries** в каждой функции компилятора «Дубины».
- **W^X**: страницы либо записываемы, либо исполняемы, никогда вместе.
- **KASLR**: ядро рандомизировано в виртуальной памяти.
- **SMEP/SMAP/UMIP** на x86_64; **PAN/PXN** на aarch64 — обязательны.
- **CET** (Indirect Branch Tracking) — где доступно.
- **Minimal TCB**: ядро + загрузчик ~< 30 KSLOC. Всё остальное — userspace.
- **Verified builds**: детерминированная сборка, подпись каждого `.дубп`.

## 8. Целевые архитектуры

| Архитектура | Машины | Загрузчик |
|---|---|---|
| x86_64 | QEMU pc, QEMU q35, реальный ПК | MBR+Stage2, UEFI |
| aarch64 | QEMU virt, Raspberry Pi 4 | UEFI (EDK2), raw |

## 9. Зависимости

Ядро — `#![no_std]`, без `alloc` (свой аллокатор). Внешние библиотеки только в стандартной библиотеке userspace и в компиляторе.
