# ДубФС — файловая система ДубинаОС

Версия 0.1.0 — этап 5 «Файловая система».

> Этот документ описывает on-disk формат и алгоритмы. Его нужно уметь читать
> в одиночку, без знаний о ДубинаОС в целом.

## 1. Цели

ДубФС создавалась с такими свойствами в порядке убывания важности:

1. **Не теряет данные при сбое питания.** Все изменения метаданных и данных
   проходят через журнал; в самом плохом случае система откатится к
   состоянию до начала транзакции.
2. **Защищает данные от случайной порчи.** Каждый блок (включая inodes,
   каталоги и журнал) защищён 32-байтной контрольной суммой BLAKE3
   (на этапе 5 — заглушка `КонтрольнаяСумма::простая`, реальный BLAKE3
   подключается на этапе 9 «Криптография»).
3. **Линейно масштабируется** на каталоги с миллионами записей за счёт
   B+-деревьев в каталогах.
4. **Простая в реализации и анализе.** Никаких extents, online-дефрагментации,
   compression — только то, что нужно.

Шифрование AES-XTS, snapshot и copy-on-write **не входят** в MVP пятого
этапа: их выносим на этап 9 после криптографического стека.

## 2. Глоссарий

| Термин | Определение |
|---|---|
| **Блок** | Фиксированный кусок диска (по умолчанию 4 КиБ). Адресуется числом — номер блока. |
| **Inode** | Запись описания файла или каталога: тип, размер, режим, времена, список блоков данных. |
| **Битмап** | Массив бит, где i-й бит = 1 значит «занято». Битмап блоков и битмап inodes — отдельные. |
| **Каталог** | Файл специального типа, хранящий записи `(имя, номер_inode)`. |
| **Журнал** | Циркулярный массив записей будущих изменений; перед применением транзакция полностью пишется в журнал и помечается как `Подтверждена`. |
| **Транзакция** | Атомарный набор изменений, видимый получателю как единое целое. |

## 3. On-disk layout

```
+-----------------------------+ блок 0
|        Суперблок            |
+-----------------------------+ блок СБ.битмап_блоков_начало
|     Битмап блоков           |
+-----------------------------+ блок СБ.битмап_inodes_начало
|     Битмап inodes           |
+-----------------------------+ блок СБ.таблица_inodes_начало
|     Таблица inodes          |
+-----------------------------+ блок СБ.журнал_начало
|     Журнал (циркулярный)    |
+-----------------------------+ блок СБ.данные_начало
|     Блоки данных            |
+-----------------------------+ блок СБ.всего_блоков
```

Размер блока зафиксирован в суперблоке (по умолчанию 4096 байт). Все остальные
поля адресуются в **номерах блоков**, не в байтах — это упрощает арифметику и
автоматически подстраивается под другой размер блока.

### 3.1 Суперблок (1 блок)

Размер: 256 байт «полезной части» в начале блока, остальное — нули и контрольная
сумма в самом конце.

```rust
struct Суперблок {
    магия: u64,                        // 0xD0BA_F5_0BE5 ("ДубинаФС")
    версия_диска: u32,                 // 1
    флаги: u32,                        // см. ниже
    размер_блока: u32,                 // 4096
    всего_блоков: u64,                 // включая суперблок
    всего_inodes: u64,
    свободных_блоков: u64,
    свободных_inodes: u64,
    битмап_блоков_начало: u64,
    битмап_блоков_длина: u64,          // в блоках
    битмап_inodes_начало: u64,
    битмап_inodes_длина: u64,
    таблица_inodes_начало: u64,
    таблица_inodes_длина: u64,
    журнал_начало: u64,
    журнал_длина: u64,                 // в блоках
    данные_начало: u64,
    inode_корня: u64,                  // обычно 1
    последняя_монтаж_метка: u64,       // unix timestamp
    счётчик_монтажей: u64,
    метка: [u8; 32],                   // UTF-8 имя ФС, дополнено нулями
    зарезервировано: [u8; 64],
    контрольная_сумма: [u8; 32],       // BLAKE3 от всего блока с занулённым
                                       // полем «контрольная_сумма»
}
```

Флаги (битовое поле):

| Бит | Имя | Значение |
|---|---|---|
| 0 | ЧИСТО | Размонтирован корректно. После монтирования сбрасывается, при размонтировании выставляется. |
| 1 | ЖУРНАЛ_ТРЕБУЕТ_ПРОИГРЫВАНИЯ | После монтирования с флагом 0 в этом поле — нужен replay журнала. |

### 3.2 Битмап блоков

Один бит на блок диска. Бит 0 битмапа описывает блок 0 диска (суперблок —
всегда занят). Длина в блоках вычисляется при `мкдубфс` и сохраняется в
суперблоке.

### 3.3 Битмап inodes

Один бит на inode. Бит 0 — inode номер 0 (зарезервированный, никогда не
используется), бит 1 — корневой каталог.

### 3.4 Таблица inodes

Каждый inode занимает 256 байт (16 inodes на блок 4 КиБ).

```rust
struct ИнодДиск {
    тип_и_режим: u32,        // 4 бита тип, 12 бит режим (rwx user/group/other)
    флаги: u32,
    размер: u64,             // байт; для каталога — суммарный размер записей
    время_создания: u64,     // unix timestamp в наносекундах
    время_изменения: u64,
    время_доступа: u64,
    ссылок: u32,             // hard-link count
    хозяин: u32,
    группа: u32,
    блоков_занято: u64,
    прямые_блоки: [u64; 12], // прямые ссылки на блоки данных
    косвенный: u64,          // блок-список номеров блоков данных
    двойной_косвенный: u64,  // блок-список блоков-списков
    зарезервировано: [u8; 32],
    контрольная_сумма: [u8; 32],
}
```

Тип:

| Значение | Имя | Описание |
|---|---|---|
| 0 | СВОБОДЕН | inode не используется |
| 1 | ОБЫЧНЫЙ_ФАЙЛ | regular file |
| 2 | КАТАЛОГ | directory |
| 3 | СИМВОЛИЧЕСКАЯ_ССЫЛКА | symlink (не реализовано в MVP) |
| 4 | СПЕЦИАЛЬНОЕ_УСТРОЙСТВО | character/block device (не в MVP) |

С 12 прямыми блоками + 1 косвенным (на блок 4 КиБ помещается 512 указателей
по 8 байт) + 1 двойным косвенным получается:
`12 + 512 + 512² = 262 156` блоков на файл = ~1 ГиБ при блоке 4 КиБ. Для MVP
этого хватит.

### 3.5 Каталоги

В MVP каталог — это файл, в данных которого лежит **сортированный по хэшу
имени массив записей**:

```rust
#[repr(C)]
struct ЗаписьКаталога {
    хэш_имени: u64,      // BLAKE3-128 от UTF-8 имени, верхние 64 бита
    инод: u64,
    длина_имени: u16,
    тип: u8,             // дублируется из inode для быстрого ls
    зарезервировано: u8,
    // сразу после структуры идёт UTF-8 имя длиной `длина_имени`,
    // выровненное до 8 байт
}
```

Поиск — двоичный по хэшу. При коллизии (что крайне маловероятно для BLAKE3)
сравниваются полные имена. Запись и удаление — пересборка отсортированного
массива.

В версии 2 (после MVP) сортированный массив заменится на B+-дерево: внутренние
узлы — массивы хэшей и ссылок на дочерние блоки, листья — массивы записей,
размер узла = блок диска. Корень дерева сейчас хранится как первый
прямой блок каталога; при переходе на B+ корень будет содержать узел дерева.

### 3.6 Журнал

Циркулярный буфер из `СБ.журнал_длина` блоков. В каждом блоке — заголовок +
полезная нагрузка.

```rust
#[repr(C)]
struct ЗаголовокЗаписиЖурнала {
    магия: u64,                // 0xDB17_F5_8AE5 ("ДубФС журнал")
    тип: u32,                  // 1 = НАЧАЛО, 2 = ОБРАЗ_БЛОКА, 3 = ПОДТВЕРЖДЕНИЕ
    идентификатор_транзакции: u64,
    последовательный_номер: u64, // монотонно растущий
    блок_цели: u64,            // для ОБРАЗ_БЛОКА — номер блока на диске
    байт_данных: u32,
    зарезервировано: u32,
    контрольная_сумма: [u8; 32],
}
```

Формат транзакции в журнале:

```
[ НАЧАЛО (id=N, num=M) ]
[ ОБРАЗ_БЛОКА (id=N, блок=B1, данные) ]
[ ОБРАЗ_БЛОКА (id=N, блок=B2, данные) ]
... ещё образы ...
[ ПОДТВЕРЖДЕНИЕ (id=N, num=M+K) ]
```

Применение транзакции:
1. Все ОБРАЗ_БЛОКА записываются в журнал и сбрасываются на диск.
2. Записывается ПОДТВЕРЖДЕНИЕ.
3. Только после ПОДТВЕРЖДЕНИЯ блоки переносятся из журнала на свои настоящие
   места.
4. Когда транзакция полностью применена, в суперблоке обновляется
   `последний_примененный_id` (хранится в журнальной хвостовой записи). Это
   позволяет при следующем монтировании проиграть только незавершённые
   транзакции.

Если найден ПОДТВЕРЖДЕНИЕ без всех нужных ОБРАЗ_БЛОКА — транзакция отбрасывается
(битый журнал).

## 4. API

См. крейт `dubina-fs`. Основные операции:

| Метод | Описание |
|---|---|
| `мкдубфс(устройство, параметры)` | Создаёт новую ФС на пустом устройстве. |
| `смонтировать(устройство)` | Открывает существующую ФС, проигрывает журнал. |
| `размонтировать()` | Сбрасывает буферы, ставит флаг ЧИСТО. |
| `создать_файл(путь)` | Создаёт пустой файл; родительский каталог должен существовать. |
| `прочитать_файл(путь, смещение, буфер)` | Возвращает прочитано байт. |
| `записать_файл(путь, смещение, данные)` | Возвращает записано байт. |
| `удалить_файл(путь)` | Уменьшает счётчик ссылок, освобождает блоки при 0. |
| `создать_каталог(путь)` | Создаёт каталог. |
| `прочитать_каталог(путь)` | Возвращает итератор по `(имя, инод, тип)`. |
| `статистика()` | Возвращает свободные блоки/inodes. |
| `проверить()` | fsck-аналог: пересчитывает битмапы и контрольные суммы. |

## 5. Что не входит в MVP этапа 5

- AES-XTS шифрование (этап 9).
- Реальный BLAKE3 — пока заглушка, помеченная `TODO(этап 9)`.
- Snapshot, copy-on-write.
- Online resize.
- Симлинки и спец-устройства.
- Реальные B+-деревья (используется сортированный массив; интерфейс уже спрятан
  за `модуль каталог`, переход прозрачен).
- Драйверы блочных устройств (sata/virtio-blk) — пока только `БлокУстройствоВПамяти`.

## 6. Совместимость и эволюция

Версия on-disk формата записана в суперблоке (`версия_диска`). При
несовместимых изменениях (например, ввод B+-деревьев) `смонтировать` отказывает,
и пользователь должен запустить `мкдубфс --мигрировать`.
